# Freedom Benchmark

```bash
make freedom-benchmark SCALE=10            # OpenLakehouse: Spark, DuckDB, DataFusion
make freedom-benchmark SCALE=10 DATABRICKS_PROFILE=<profile> TABLE_ROOT=abfss://...   # + Databricks
```

The benchmark runs the 22 TPC-H queries on each engine, stores every result, and compares them. It answers two questions, in this order.

| | Question | Status |
|---|---|---|
| **Portability benchmark** | Does the workload run correctly? | primary objective |
| **Performance benchmark** | How does it perform? | secondary |

!!! warning "Unlike compute is not a platform comparison"

    A Docker stack on one laptop, a Databricks serverless job and a 16-node cluster are different machines. Timings from them show that the workload runs and roughly how long it takes. They do not support a conclusion about which platform is faster. The report labels every timing with the compute it ran on. A performance comparison is only meaningful when the environments have comparable resources, and v1 makes no such claim.

## Workload

- **Data.** TPC-H generated by the DuckDB `tpch` extension (embedded reference `dbgen`), at any scale factor. SF1 and SF10 are tested.
- **Queries.** `tpch/queries/q01.sql` … `q22.sql`, written once in the style one would use on Databricks SQL / Spark SQL: TPC-H qualification parameters, spec-style date arithmetic (`date '1998-12-01' - interval '90' day`), a CTE for Q15.
- **Engines.**

    | Platform | Engine | Access path |
    |---|---|---|
    | Databricks | Spark (Databricks Runtime, serverless job) | Unity Catalog |
    | OpenLakehouse | Apache Spark 4.1.0 via Spark Connect | Unity Catalog OSS |
    | OpenLakehouse | DuckDB 1.5.6, in-process on the host | location from UC OSS, `delta_scan` |
    | OpenLakehouse | Apache DataFusion, in-process on the host | location from UC OSS, delta-rs Arrow dataset |

## Query compatibility classification

| Class | Meaning |
|---|---|
| **PORTABLE** | Canonical SQL runs unchanged and returns the reference result |
| **ADAPTABLE** | An engine-specific variant in `tpch/queries/adapted/<engine>/` is needed, and it changes at most 20% of the lines |
| **REWRITE** | A variant is needed that changes more than 20% of the lines |
| **FAILED** | No variant returns the reference result |

The runner always tries the canonical text first and keeps that attempt in the result file, even when an adapted variant exists. An adaptation can therefore never hide a failure of the original SQL. With the current queries no adaptations were needed: all 22 run unchanged on every engine tested.

## Result files

```
benchmarks/results/
├── openlakehouse/sf10/
│   ├── spark/q01.json … q22.json, run.json
│   ├── duckdb/q01.json … q22.json, run.json
│   ├── datafusion/q01.json … q22.json, run.json
│   ├── generator.json  quality.json  gold.json
├── databricks/sf10/…            # after make databricks-fetch-results
```

Each `qNN.json` records:

```json
{
  "platform": "openlakehouse", "engine": "spark", "engine_version": "4.1.0",
  "query": "q01", "scale_factor": 10, "variant": "canonical",
  "success": true, "duration_s": 9.83, "durations_s": [9.83],
  "row_count": 4, "error": null, "timestamp": "2026-10-04T…Z",
  "environment": { "delta_version": "4.3.1", "unitycatalog_server": "v0.5.0",
                   "spark_conf": {"spark.executor.cores": "6", "…": "…"},
                   "host_cpus": 8, "host_memory_gb": 13.6, "…": "…" },
  "columns": ["l_returnflag", "…"], "rows": [["A", "…"]],
  "canonical": null
}
```

`duration_s` is the median of `REPEATS` timed runs (default 3). It is measured around `collect()` / `fetchall()`, so it includes planning, execution and transferring the result to the client.
